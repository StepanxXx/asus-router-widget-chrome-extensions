# План міграції розширення на React + Vite

## 1. Поточний стан

Розширення використовує Manifest V3, але не має package manager, bundler або системи тестування.

Поточна архітектура:

- `popup.html` і `popup.js` створюють дві кнопки: `clients` та `networks`;
- popup через `chrome.scripting` послідовно інжектить CSS і JavaScript у сторінку роутера;
- модулі публікують API через глобальні змінні `AsusRouter*` та `Diagram`;
- UI створюється через ручні DOM-операції та `innerHTML`;
- дані оновлюються через `setInterval` кожні 2 секунди;
- відповіді ASUS перетворюються з JavaScript-подібного тексту на JSON;
- у проєкті немає автоматичних тестів, типізації та статичного аналізу.

## 2. Цілі міграції

- перейти на React і TypeScript;
- використовувати Vite для development і production build;
- прибрати глобальні runtime-залежності `AsusRouter*`;
- замінити ручне створення DOM на React-компоненти;
- зробити polling керованим і гарантовано очищати його після закриття UI;
- ізолювати стилі розширення від стилів сторінки ASUS;
- додати валідацію відповідей роутера;
- додати unit- і component-тести;
- зберегти сумісність із Manifest V3 та поточну функціональність.

## 3. Рекомендований стек

### Основні залежності

- **React 19** — компонентний UI;
- **TypeScript** — типізація API, стану та повідомлень розширення;
- **Vite** — development server і production build;
- **`@crxjs/vite-plugin`** — інтеграція Vite з Manifest V3;
- **TanStack Query** — polling, кеш, loading/error state і скасування запитів;
- **Zod** — валідація та нормалізація даних роутера;
- **CSS Modules** — локальна область дії стилів;
- **Vitest** — unit-тести;
- **React Testing Library** — тести React-компонентів;
- **ESLint + Prettier** — перевірка і форматування коду.

### Опціональні залежності

- **Recharts** — можлива заміна власного canvas-графіка після основної міграції;
- **`webextension-polyfill`** — якщо буде потрібна підтримка Firefox;
- **Zustand** — тільки якщо з'явиться складний спільний стан між компонентами.

На першому етапі не потрібні Redux, React Router або великий UI-фреймворк.


Popup має надсилати команду content script, а content script — монтувати відповідний React-екран. Це замінить послідовну інжекцію глобальних JS-файлів.

## 5. Етапи міграції

### Етап 1. Зафіксувати поточну поведінку

Перед рефакторингом потрібно створити acceptance checklist:

- popup показує кнопки `clients` і `networks`;
- натискання відкриває відповідний діалог;
- повторне відкриття закриває попередній діалог;
- дані оновлюються раз на 2 секунди;
- polling припиняється після закриття;
- правильно розраховуються RX/TX, швидкість і 30 останніх точок;
- підтримуються LAN, 2.4 GHz, 5 GHz і 6 GHz;
- розширення працює на підтримуваних моделях та прошивках ASUS.

Також потрібно зберегти анонімізовані відповіді таких endpoint-ів як test fixtures:

- `update_clients.asp`;
- `getTraffic.asp`;
- `update.cgi` з `output=netdev`.

### Етап 2. Додати Vite та TypeScript

Створити:

- `package.json`;
- `vite.config.ts`;
- `tsconfig.json`;
- `manifest.ts`;
- конфігурації ESLint і Prettier;
- npm-скрипти `dev`, `build`, `typecheck`, `lint` і `test`.

Результат етапу: `npm run build` створює директорію `dist/`, яку можна завантажити у Chrome як unpacked extension.

Поведінку основного UI на цьому етапі змінювати не потрібно.

### Етап 3. Перенести popup на React

Замінити `popup.js` на React-компонент:

- відобразити дві типізовані кнопки;
- отримувати активну вкладку;
- надсилати `open-clients` або `open-networks` через `chrome.tabs.sendMessage()`;
- показувати зрозумілу помилку для непідтримуваної сторінки;
- закривати popup після успішної команди.

Повідомлення варто описати через TypeScript discriminated union.

### Етап 4. Створити єдиний content script

Content script повинен:

- слухати повідомлення popup;
- створювати один mount container;
- монтувати React через `createRoot`;
- перемикати активний екран;
- коректно виконувати `root.unmount()`;
- не створювати дублікати діалогів.

Рекомендовано монтувати UI у Shadow DOM. Це ізолює компоненти від CSS сторінки ASUS і дозволить прибрати інжекцію повного `bootstrap.css`.

### Етап 5. Перенести data layer у TypeScript

Потрібно перетворити поточні data stores на незалежні модулі:

- API-функції для виконання запитів;
- parser-и текстових відповідей ASUS;
- Zod-схеми для валідації;
- чисті transformer-и для обчислення швидкості та історії;
- типи клієнтів, мереж, traffic samples і API responses;
- спільні функції форматування Mbps та MB.

Рекомендований pipeline:

```text
fetch raw text → parse → validate → calculate delta → render
```

Parser error повинен переходити у контрольований error state, а не зупиняти весь UI.

### Етап 6. Замінити `setInterval` на TanStack Query

Створити hooks:

- `useClients()`;
- `useClientTraffic()`;
- `useNetworks()`.

Базові налаштування:

- `refetchInterval: 2000`;
- скасування запиту через `AbortSignal`;
- контроль повторних спроб;
- polling тільки поки відповідний екран відкритий;
- loading, error і stale states;
- захист від накладання повільних запитів.

Розрахунок delta та traffic history потрібно залишити в чистій функції або reducer, а не переносити в JSX.

### Етап 7. Перенести UI на React-компоненти

#### Clients

- `ClientsDialog`;
- `ClientsTable`;
- `ClientColumn`;
- `ClientCard`;
- `ConnectionBadge`;
- `TrafficValue`;
- `RssiIndicator`;
- `TrafficChart`.

#### Networks

- `NetworksDialog`;
- `NetworkTable`;
- `NetworkRow`;
- `TrafficChart`.

#### Спільні компоненти

- `Dialog`;
- `LoadingState`;
- `ErrorState`;
- `CloseButton`;
- `DirectionIndicator`.

Під час міграції потрібно прибрати ручні `appendChild`, очищення контейнерів і більшість використань `innerHTML`. Текстові дані роутера мають відображатися як React text nodes.

### Етап 8. Мігрувати графіки

Безпечна послідовність:

1. Обгорнути поточний `Diagram` у React-компонент із `canvas`, `ref` та `useEffect`.
2. Після стабілізації оцінити перехід на Recharts.

Потрібно окремо обробити:

- порожній масив точок;
- `max === min`;
- від'ємний delta після скидання лічильника роутера;
- великий проміжок між запитами;
- спробу малювання після unmount компонента.

Для першого релізу рекомендовано залишити наявний canvas-графік, щоб зменшити обсяг одночасних змін.

### Етап 9. Переробити стилі

- видалити залежність від повного `bootstrap.css`;
- перенести потрібні стилі у CSS Modules або stylesheet Shadow DOM;
- додати CSS variables для кольорів, spacing і typography;
- перевірити вузькі екрани та велику кількість клієнтів;
- не використовувати CSS-класи сторінки ASUS як залежність;
- перевірити, що стилі розширення не змінюють основний UI роутера.

### Етап 10. Додати тести

#### Unit tests

- parser клієнтів;
- parser client traffic;
- parser network traffic;
- розрахунок швидкості;
- напрямки RX/TX для INTERNET, LAN і Wi-Fi;
- обрізання history до 30 точок;
- RSSI mapping;
- форматування одиниць;
- reset або overflow лічильників;
- неповні та некоректні відповіді роутера.

#### Component tests

- loading, error і data states;
- сортування клієнтів;
- закриття діалогу;
- cleanup polling;
- відображення невідомих або відсутніх полів.

#### Manual smoke test

- зібрати `dist/`;
- завантажити як unpacked extension;
- перевірити popup;
- перевірити обидва діалоги на реальному роутері;
- перевірити повторне відкриття та закриття;
- перевірити відсутність помилок у popup і page console.

### Етап 11. Перевірити manifest і permissions

Потрібно визначити:

- чи залишається потрібним `activeTab`;
- чи можна замінити програмну інжекцію декларативним content script;
- які `host_permissions` потрібні для адрес роутерів;
- які URL та протоколи підтримуються;
- чи відповідає збірка CSP Manifest V3;
- чи не виконується код, отриманий у відповіді роутера.

Адреси ASUS можуть відрізнятися, тому `host_permissions` потрібно погодити з реальними сценаріями використання.

### Етап 12. Видалити legacy-код

Після переходу обох екранів видалити:

- глобальні `AsusRouter*` API;
- `ensureGlobalScript()`;
- послідовну інжекцію JavaScript-файлів;
- старі controllers та UI builders;
- дублікати helpers і styles config;
- повний Bootstrap, якщо він більше не використовується;
- застарілі CSS-файли.

## 6. Рекомендована послідовність релізів

Щоб спростити перевірку та rollback, міграцію варто виконувати вертикальними зрізами:

1. Vite + TypeScript + збірка наявного функціоналу.
2. React popup і система повідомлень.
3. React-версія Networks.
4. React-версія Clients.
5. Спільні компоненти та ізоляція стилів.
6. Тести й обробка помилок.
7. Видалення legacy-коду та Bootstrap.
8. Production build і smoke test.

Після кожного кроку розширення повинно залишатися придатним до ручної перевірки.

## 7. Основні ризики

### Контекст виконання

Content script працює в isolated world, а запити до сторінки роутера можуть залежати від origin, cookies та авторизації. Це потрібно перевірити прототипом до масової міграції.

### Нестабільний формат API ASUS

Endpoint-и повертають JavaScript-подібний текст, а не надійний JSON. Parser-и необхідно тестувати на кількох версіях прошивки.

### Конфлікти CSS

Сторінка роутера та Bootstrap можуть змінювати вигляд React-компонентів. Shadow DOM або чітка ізоляція класів є важливою частиною міграції.

### Регресії в обчисленні traffic

Логіка напрямків INTERNET/LAN і обчислення delta має специфічні правила. Її потрібно покрити тестами до переписування UI.

### Надмірна міграція

Не варто одночасно переписувати UI, parser-и, графіки та дизайн. Спочатку потрібно відтворити поточну поведінку, а покращення робити окремими змінами.

## 8. Критерії завершення

Міграція вважається завершеною, коли:

- відсутні runtime-глобали `AsusRouter*`;
- відсутній ручний ланцюжок інжекції JS-файлів;
- popup і content UI працюють через типізовані повідомлення;
- polling гарантовано припиняється після закриття UI;
- parser errors відображаються користувачу;
- стилі розширення не впливають на сторінку ASUS;
- `npm run build` проходить;
- `npm run typecheck` проходить;
- `npm run lint` проходить;
- `npm run test` проходить;
- `dist/` завантажується як unpacked Manifest V3 extension;
- Clients і Networks пройшли smoke test на реальному роутері.

## 9. Орієнтовна оцінка

- інфраструктура Vite/TypeScript: **0.5–1 день**;
- React popup і messaging: **0.5 дня**;
- data layer, типи та parser-и: **1–2 дні**;
- Networks UI: **0.5–1 день**;
- Clients UI: **1–2 дні**;
- стилі та Shadow DOM: **0.5–1 день**;
- тести, cleanup і smoke test: **1–2 дні**.

Загальна оцінка: **5–8 робочих днів** для повної міграції або **2–3 дні** для MVP без повного тестового покриття та додаткового покращення UI.

## 10. Перший практичний крок

Першу ітерацію варто обмежити такими завданнями:

1. Додати Vite, TypeScript і `@crxjs/vite-plugin`.
2. Перенести manifest у конфігурацію збірки.
3. Перенести popup на React.
4. Додати типізовані повідомлення між popup і content script.
5. Залишити поточну логіку Clients і Networks без функціональних змін.

Це створить основу для подальшої міграції без одночасного переписування найскладнішої логіки.
